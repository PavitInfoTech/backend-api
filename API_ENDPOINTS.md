# Backend API Contract

**Verified against the registered routes, controllers, middleware, models, migrations, mailables, services, and feature tests on 2026-07-30.**

This file describes the behavior implemented in this repository. It is an implementation contract, not a description of an ideal future API. Where the current code has a known flow defect, it is called out explicitly rather than hidden behind an example.

## Scope

The API routes are defined in `routes/api.php`. The setup wizard, admin login, and settings pages are ordinary web routes defined in `routes/web.php`; they are listed in the final appendix but are not JSON API endpoints.

The API currently exposes:

- health, authentication, OAuth, profiles, plans, payments, AI, mail, maps, CAPTCHA, and an API 404 fallback;
- Bearer-token authentication through Laravel Sanctum for protected routes;
- browser redirects for selected OAuth, email-verification, and newsletter flows.

## Base URL and route prefix

Every API route is registered under `/api`, regardless of environment or domain configuration. There is no domain-root API alias.

Examples:

```text
Local/default:  http://localhost:8000/api/auth/login
API subdomain:  https://api.example.com/api/auth/login
```

`API_DOMAIN` may be configured as a deployment host or CORS origin, but it does not change the `/api` prefix. `APP_URL` is used when the application generates URLs and `FRONTEND_URL` is used for browser redirects and reset links.

## Middleware and authentication

All API routes use Laravel's `api` middleware group. Protected routes additionally use `auth:sanctum`. Browser OAuth/link routes also add the `web` middleware so Socialite can use the session/state flow.

For a protected API request:

```http
Authorization: Bearer <sanctum_plain_text_token>
Accept: application/json
```

Sanctum stores only a hash of the token in the database. Tokens are created on registration, login, OAuth login, and password reset. The current implementation does not expire tokens automatically and does not invalidate previous tokens when a user logs in again.

The public `POST /api/auth/logout` route is intentionally not behind `auth:sanctum`. With a valid bearer token it revokes the current token; it can also revoke the token represented by the `api_token` cookie. JSON requests receive JSON; browser-style requests are redirected to `FRONTEND_URL/auth/logout`.

## Response envelopes

Most controller responses use one of these envelopes.

### Success

```json
{
  "status": "success",
  "message": "Human-readable message",
  "data": {},
  "code": 200,
  "timestamp": "2026-07-30T12:00:00+00:00"
}
```

`data` may be an object, array, paginator object, or `null`. `code` matches the HTTP status. Timestamps are generated by the application in UTC and use ISO-8601 format.

The asynchronous AI response is an exception: it is a raw 202 response with `status: "accepted"` and does not include `code` or `timestamp`.

### Custom error

```json
{
  "status": "error",
  "message": "Error description",
  "errors": null,
  "code": 400,
  "timestamp": "2026-07-30T12:00:00+00:00"
}
```

### Validation error

```json
{
  "status": "error",
  "message": "The given data was invalid.",
  "errors": {
    "field": ["The field is required."]
  },
  "code": 422,
  "timestamp": "2026-07-30T12:00:00+00:00"
}
```

The API exception handler also formats authentication, authorization, 404, 405, and other HTTP errors into the same JSON shape when the request is recognized as an API request. Browser redirect responses from the OAuth and verification flows remain redirects when the controller deliberately returns one.

# Authentication

## Register

```http
POST /api/auth/register
```

Request JSON:

```json
{
  "username": "john_doe",
  "first_name": "John",
  "last_name": "Doe",
  "email": "john@example.com",
  "password_hash": "<exactly 64 characters>",
  "password_hash_confirmation": "<same value>",
  "turnstile_token": "optional",
  "recaptcha_token": "optional"
}
```

Validation:

- `username`: required, string, max 255, unique in `users.username`;
- `first_name` and `last_name`: nullable strings, max 255;
- `email`: required, valid email, unique in `users.email`;
- `password_hash`: required string of length 64;
- `password_hash_confirmation`: required and must match `password_hash`.

The API expects the client to send the SHA-256 representation as `password_hash`. The backend stores that value directly; it does not hash it again. The implementation does not enforce hexadecimal characters, only length.

If Turnstile or reCAPTCHA is enabled, CAPTCHA-related rules are added to the request. The token fields are currently declared `sometimes`; clients should send the valid token in `turnstile_token` or `recaptcha_token` whenever CAPTCHA protection is enabled.

Success: HTTP 201, message `Registered. Please check your email to verify your account.`. `data` contains `user` and a new Sanctum `token`. The user is created, a token is created, and the verification email is sent synchronously through the configured mailer.

## Login

```http
POST /api/auth/login
```

```json
{
  "email": "john@example.com",
  "password_hash": "<exactly 64 characters>"
}
```

Success: HTTP 200, message `Logged in`, with `data.user` and `data.token`. Credentials are compared to the stored string with `hash_equals`. Email verification is not required by this endpoint. Each successful login creates another token; previous tokens remain valid until revoked.

Invalid credentials return HTTP 401 with message `Invalid credentials`. Validation failures return HTTP 422.

## Logout

```http
POST /api/auth/logout
```

This route is public at the routing layer. For an authenticated bearer request, the current access token is deleted. If only an `api_token` cookie is present, the matching Sanctum token hash is also deleted. The cookie is forgotten in the response.

With `Accept: application/json` or a JSON request, success is HTTP 200 with message `Logged out` and `data: null`. A browser-style request is redirected to `FRONTEND_URL/auth/logout` instead of receiving the JSON envelope.

## Send verification email

```http
POST /api/auth/verify/send
```

If the request has a logged-in user, no body is required and the email is taken from that user. Otherwise, the request must contain:

```json
{ "email": "john@example.com" }
```

The endpoint is public and is not throttled. Unknown emails return a generic HTTP 200 success. Already verified users return HTTP 200 with message `Email already verified`. Unverified users receive a new email and message `Verification email sent`.

## Verify email

```http
GET /api/auth/verify/{token}
```

The token is looked up in `email_verification_tokens`. Invalid tokens return HTTP 400, not 404. The implementation does not check the token age. A matching user is marked verified and the token is deleted.

If the request does not want JSON, the endpoint redirects to `FRONTEND_URL/auth/verified`. With an explicit JSON request it returns HTTP 200, message `Email verified`, and `data.user`.

## Request password reset

```http
POST /api/auth/password/forgot
```

```json
{
  "email": "john@example.com",
  "turnstile_token": "optional when enabled",
  "recaptcha_token": "optional when enabled"
}
```

The endpoint is public and is not throttled. For an existing user, it writes a plaintext random token to `password_reset_tokens`, sends `PasswordResetMail`, and returns HTTP 200 with message `Password reset link sent if account exists`. For an unknown user, it returns HTTP 200 with message `If an account exists we will send a password reset link`. This avoids revealing whether an address exists.

## Reset password

```http
POST /api/auth/password/reset
```

```json
{
  "email": "john@example.com",
  "token": "token_from_auth_password_forgot",
  "password_hash": "<exactly 64 characters>",
  "password_hash_confirmation": "<same value>"
}
```

The token must match the row for the supplied email and must be no more than 120 minutes old. Invalid or expired tokens return HTTP 422. A missing user returns HTTP 404. On success, the token row is deleted, the password hash string is replaced, and a new Sanctum token is issued. Existing unrelated Sanctum tokens are not revoked. Success is HTTP 200 with `data.user` and `data.token`.

## Change password

```http
POST /api/auth/password/change
Authorization: Bearer <token>
```

```json
{
  "current_password_hash": "<exactly 64 characters>",
  "password_hash": "<exactly 64 characters>",
  "password_hash_confirmation": "<same value>"
}
```

The current password must match exactly. A wrong current password returns HTTP 422 with message `Current password is incorrect`. Success is HTTP 200 with message `Password changed successfully` and `data: null`.

## OAuth token exchange

### Google

```http
POST /api/auth/google/token
```

Accepted request fields:

- `code` required when `credential` is absent;
- `credential` required when `code` is absent;
- `redirect_uri` optional but, when present, must be a URL.

The `code` path exchanges the authorization code server-side and obtains the Google user. The `credential` path validates a Google ID token through Google's token-info endpoint. Success is HTTP 200 with message `Authenticated via Google`, `data.user`, and `data.token`. Provider failures return HTTP 400 with `Google authentication failed`.

### GitHub

```http
POST /api/auth/github/token
```

Accepted request fields:

- `code` required when `access_token` is absent;
- `access_token` required when `code` is absent;
- `redirect_uri` optional but, when present, must be a URL.

Success is HTTP 200 with message `Authenticated via Github`, `data.user`, and `data.token`. Provider failures return HTTP 400 with `GitHub authentication failed`.

## Browser OAuth redirect and callback

For each provider, the following public routes use the `web` middleware for Socialite session state:

```text
GET /api/auth/google/redirect
GET /api/auth/google/callback
GET /api/auth/github/redirect
GET /api/auth/github/callback
```

The redirect route returns a 302 redirect to the provider. The callback exchanges the provider response and creates or finds a local user. If the request explicitly prefers JSON, the callback returns the same `data.user` and `data.token` envelope as the token exchange. Otherwise it redirects to:

```text
FRONTEND_URL/auth/complete?token=<plain_sanctum_token>
```

Provider errors return HTTP 400 JSON. The current implementation places the plain API token in the redirect query string; consumers should treat this as a security-sensitive implementation detail.

## Link and unlink OAuth providers

Linking requires both a Sanctum-authenticated route and the browser session middleware:

```text
GET /api/auth/link/google/redirect
GET /api/auth/link/google/callback
GET /api/auth/link/github/redirect
GET /api/auth/link/github/callback
```

The redirect starts provider consent. The callback attaches `provider_name`, `provider_id`, and the provider avatar to the current user and returns HTTP 200 JSON with `data.user` and a provider-specific linked message. It does not issue a new API token.

Unlinking:

```http
POST /api/auth/unlink
Authorization: Bearer <token>
```

```json
{ "provider": "google" }
```

The provider field is required. If the provider is not the user's currently linked provider, the endpoint returns HTTP 400 with `Provider not linked`. Otherwise it clears both provider fields and returns HTTP 200 with `data: null`.

# Profiles

## Current profile

```http
GET /api/user
Authorization: Bearer <token>
```

Success is HTTP 200 with message `User profile` and `data` equal to the authenticated user model. `password` and `remember_token` are hidden. The avatar is normalized to an absolute URL when possible.

## Update profile

```http
PUT /api/user
Authorization: Bearer <token>
```

All fields are optional:

```json
{
  "username": "john_doe_updated",
  "first_name": "Johnny",
  "last_name": "Smith",
  "email": "new@example.com",
  "avatar": "https://example.com/avatar.jpg"
}
```

`username` is a string with max length 255 and unique except for the current user. `first_name` and `last_name` are strings with max length 255. `email` must be a valid unique email. `avatar` must be a valid URL. Success is HTTP 200 with message `Profile updated` and the updated user model in `data`.

## Upload avatar

```http
POST /api/user/avatar
Authorization: Bearer <token>
Content-Type: multipart/form-data
```

Form field:

```text
avatar=<image file>
```

The file must be an image with extension/type `jpg`, `jpeg`, `png`, `gif`, or `webp`, and must be no larger than 5120 KB. It is stored on the `public` disk under `avatars/{user_id}`. The previous locally stored avatar is deleted when possible.

Success is HTTP 200 with:

```json
{
  "status": "success",
  "message": "Avatar uploaded",
  "data": { "avatar_url": "https://example.com/storage/avatars/1/file.jpg" },
  "code": 200,
  "timestamp": "..."
}
```

The upload endpoint does not return the full user object. Missing or invalid files are normally validation errors (HTTP 422); the controller's HTTP 400 `No file uploaded` branch is reached only if validation passes but the file object is unavailable.

## Public profile

```http
GET /api/users/{id}/public
```

Success is HTTP 200 with message `Public profile` and exactly these fields in `data`: `id`, `username`, `first_name`, `last_name`, `avatar`, and `created_at`. Email, password, plan, provider data, and other private fields are not returned. A missing user returns HTTP 404 with `User not found`.

## Delete account

```http
DELETE /api/user
Authorization: Bearer <token>
```

The controller attempts to delete the locally stored avatar, deletes all personal access tokens, and deletes the user. Payments are removed by the database foreign-key cascade when the migration is installed with that constraint. Success is HTTP 200 with message `Account deleted` and `data: null`.

# Subscription plans and payments

## Plan object

Subscription plan responses are serialized from the `SubscriptionPlan` model. The current schema contains:

```text
id, name, slug, description, price, monthly_price, yearly_price,
currency, interval, trial_days, features, is_active, popular,
created_at, updated_at
```

`price`, `monthly_price`, and `yearly_price` are decimal strings in JSON because of the model casts. `features` is an array. `interval` is `monthly`, `yearly`, or `one-time`.

## List plans

```http
GET /api/subscription-plans
```

Returns only plans where `is_active=true`, ordered by legacy `price` ascending. Success is HTTP 200 with message `Subscription plans retrieved` and an array in `data`.

## Get one plan

```http
GET /api/subscription-plans/{slug}
```

Looks up any plan by slug, including inactive plans. Success is HTTP 200 with the default success message `OK` and the plan in `data`. A missing plan returns HTTP 404 with `Subscription plan not found`.

## Create plan

```http
POST /api/subscription-plans
```

This route is public in the current implementation; no Sanctum or admin authorization is applied.

Accepted fields:

```json
{
  "name": "Professional",
  "slug": "professional",
  "description": "Plan description",
  "desc": "Alternative description field",
  "price": 19.99,
  "monthly_price": 19.99,
  "yearly_price": 199.99,
  "currency": "USD",
  "interval": "monthly",
  "trial_days": 14,
  "features": ["Feature one"],
  "is_active": true,
  "popular": false
}
```

`name` and `slug` are required. `slug` must be unique. Other fields are optional; defaults are currency `USD`, interval `monthly`, `is_active=true`, and `popular=false`. `desc` is copied to `description` when `description` is absent. Legacy `price` is mapped to the monthly or yearly field based on `interval`, and `price` is backfilled from the new pricing fields when absent.

Success is HTTP 201 with message `Subscription plan created` and the created plan in `data`.

## Update plan

```http
PUT /api/subscription-plans/{id}
```

This route is also public. The body is a partial update using the same fields as create; no field is required. A missing numeric ID returns HTTP 404 with `Subscription plan not found`. Success is HTTP 200 with message `Subscription plan updated` and the plan in `data`.

## Delete plan

```http
DELETE /api/subscription-plans/{id}
```

This route is public. The controller attempts to block deletion by querying the `SubscriptionPlan::subscriptions()` relation for an active record. In the current model that relation is a generic `hasMany(Payment::class)` relation whose default foreign key is `subscription_plan_id`, but the payments schema has no `subscription_plan_id` column. With the current migrations, the query therefore fails before deletion and the route normally produces an unhandled database error/HTTP 500. A missing plan is handled first and returns HTTP 404 with `Subscription plan not found`.

## Subscribe to a plan

```http
POST /api/subscriptions
Authorization: Bearer <token>
```

```json
{
  "plan_slug": "professional",
  "payment_method": {
    "card_number": "4242424242424242",
    "expiry_month": "12",
    "expiry_year": "28",
    "cvv": "123",
    "card_holder": "John Doe"
  },
  "billing_address": {
    "street": "123 Main Street",
    "city": "New York",
    "state": "NY",
    "zip": "10001",
    "country": "US"
  }
}
```

Validation requires `plan_slug`, the full `payment_method` object, card number length 13–19, two-character expiry month/year, CVV length 3–4, and card holder. `billing_address` is optional and only validated as an array. The plan slug may be unknown; an unknown slug creates a zero-price placeholder plan.

For a paid plan, the sandbox gateway validates card format, expiry, CVV length, and special test-card prefixes. For a zero-price plan, payment is simulated without calling the gateway. A payment row is created with `plan_name`, `status=completed`, and type `subscription` or `one-time`, and the user's `current_plan` is overwritten with the selected slug.

Success is HTTP 201, message `Payment processed successfully`, and:

```json
{
  "payment": { "transaction_id": "TXN_...", "status": "completed", "plan_name": "professional" },
  "message": "Subscription payment processed — plan set on user account"
}
```

Payment failures from the sandbox gateway return HTTP 400. Validation failures return HTTP 422. There is no separate subscription table or subscription cancellation endpoint.

## Process one-time payment

```http
POST /api/payments/process
Authorization: Bearer <token>
```

Required fields:

```json
{
  "amount": 50.00,
  "currency": "USD",
  "description": "One-time payment",
  "payment_method": {
    "card_number": "4242424242424242",
    "expiry_month": "12",
    "expiry_year": "28",
    "cvv": "123",
    "card_holder": "John Doe"
  },
  "metadata": { "reference": "internal-reference" }
}
```

`amount` must be numeric from 0.50 through 999999.99. `currency` is optional and must be three characters when supplied. `description` is optional, max 500 characters. `metadata` is optional and must be an array. The card fields have the same format validation as subscription payment.

Success is HTTP 201 with message `Payment processed successfully` and the payment model in `data`. The payment has `type=one-time`, `status=completed`, a generated `TXN_...` transaction ID, and no `gateway_response` field in serialized output because that field is hidden. Gateway failures return HTTP 400.

## List payment history

```http
GET /api/payments
Authorization: Bearer <token>
```

The endpoint returns the authenticated user's payments, newest first, using Laravel's fixed `paginate(20)`. The paginator is nested in `data` and includes keys such as `current_page`, `data`, `first_page_url`, `last_page`, `per_page`, `total`, and navigation URLs. There is no controller support for the documented `status`, `limit`, `offset`, `sort`, or `filter` query parameters; only Laravel's standard `page` query behavior applies.

## Get last purchased plan

```http
GET /api/payments/last-plan
Authorization: Bearer <token>
```

The endpoint finds the latest payment for the user with a non-null `plan_name`. With no matching payment it returns HTTP 200, message `No plan purchase found`, and:

```json
{ "plan": null, "payment": null }
```

With a matching payment it returns `data.plan` as the plan model, or `{ "slug": "..." }` if the plan no longer exists, plus `data.payment`.

## Verify payment

```http
GET /api/payments/{transactionId}
Authorization: Bearer <token>
```

Only the payment belonging to the authenticated user can be retrieved. A missing or foreign transaction returns HTTP 404 with `Payment not found`. Success is HTTP 200 with:

```json
{
  "payment": { "transaction_id": "TXN_..." },
  "verified": true,
  "gateway_status": { "valid": true, "status": "completed", "sandbox": true }
}
```

The sandbox gateway treats transaction IDs beginning with `TXN_` as valid, but the payment must still exist for the current user.

## Refund payment

```http
POST /api/payments/refund/{transactionId}
Authorization: Bearer <token>
```

Optional body:

```json
{ "reason": "Requested refund" }
```

Only the owner can refund a payment. It must currently have `status=completed`; already-refunded or other statuses return HTTP 400. The sandbox produces a refund transaction ID, then the controller updates the original payment to `status=refunded` and stores refund details in its `metadata`. It does not create a separate refund payment row.

Success is HTTP 200 with message `Refund processed successfully` and the updated payment model in `data`.

## Revert or change current plan

```http
POST /api/payments/revert-plan
Authorization: Bearer <token>
```

```json
{
  "to_plan": "free",
  "reason": "Downgrade requested"
}
```

`to_plan` is optional and nullable. When present, it must exist in `subscription_plans`. When omitted or null, `current_plan` is cleared. The controller creates a zero-value `type=revert` payment-like audit row and updates the user. Success is HTTP 200, message `Plan reverted`, with `data.payment` and `data.user`. The request field is `to_plan`, not `plan_slug`.

## Payment webhook

```http
POST /api/payments/webhook
```

```json
{
  "event_type": "payment.completed",
  "transaction_id": "TXN_...",
  "payload": {}
}
```

`event_type` and `transaction_id` are required. `payload` is optional and must be an array when supplied. The sandbox signature verifier accepts a missing or arbitrary `X-Webhook-Signature`; this is not production-grade signature verification.

`payment.completed` marks an existing payment completed and sets `paid_at`. `payment.failed` marks an existing payment failed. Unknown event types are accepted without updating a payment. The endpoint always returns HTTP 200 for valid input with message `Webhook processed` and `data.received=true` plus `data.event_type`.

# AI

## Generate

```http
POST /api/ai/generate
```

This route is public and uses the named `ai` limiter. The limit is `AI_RATE_LIMIT_PER_MINUTE` per authenticated user ID or IP address, defaulting to 60 per minute. No other API routes in `routes/api.php` have a named throttle.

The request must contain `prompt` or `messages`:

```json
{
  "prompt": "Write a short poem",
  "model": "gpt-4o-mini",
  "max_tokens": 256,
  "async": false
}
```

or:

```json
{
  "messages": [
    { "role": "system", "content": "You are helpful" },
    { "role": "user", "content": "Hello" }
  ],
  "model": "gpt-4o-mini",
  "max_tokens": 256,
  "async": false
}
```

Validation:

- `prompt`: required when `messages` is absent, string, max 5000;
- `messages`: required when `prompt` is absent, array;
- `messages.*.role`: optional string;
- `messages.*.content`: optional and not type-restricted by validation;
- `model`: optional string, max 255;
- `max_tokens`: optional integer from 1 to 2048;
- `async`: optional boolean.

The controller strips ASCII control characters from prompt/message content, stores an `ai_requests` row, and calls the configured Gorq-compatible service. The default model is read from the database setting `gorq_default_model` or `GORQ_DEFAULT_MODEL`, falling back to `gpt-4o-mini`.

### Synchronous result

With `async=false` or no `async` field, the provider result is returned inside the normal success envelope, HTTP 200, message `AI generation result`. The exact `data` shape is the JSON returned by the configured provider and is not fixed by this API.

Provider failures are stored as failed requests and return HTTP 500 with message `AI provider error`. The `errors` object includes the normalized payload and a `gorq_response` object.

### Asynchronous result

With `async=true`, a queue job is dispatched and the endpoint returns HTTP 202 in this exact non-standard shape:

```json
{
  "status": "accepted",
  "message": "Request accepted, processing",
  "data": {
    "job_id": 123,
    "status_url": "http://localhost/api/ai/jobs/123/status"
  }
}
```

The job ID is the integer primary key of `ai_requests`, not a UUID. The status URL always uses the `/api` form, including when `API_DOMAIN` is set.

## AI job status

```http
GET /api/ai/jobs/{id}/status
```

This endpoint is public and does not check ownership. A missing row returns HTTP 404 with `Job not found`. A matching row returns the normal success envelope, message `AI job status`, and:

```json
{
  "id": 123,
  "status": "pending|running|finished|failed",
  "result": {},
  "error": {},
  "meta": {},
  "created_at": "...",
  "updated_at": "..."
}
```

`result` and `error` are decoded JSON when possible. There is no `progress`, `completed` status, `response`, or `tokens_used` field added by this controller.

# Email and messaging

## Contact form

```http
POST /api/mail/contact
```

```json
{
  "name": "John Doe",
  "email": "john@example.com",
  "message": "I have a question",
  "turnstile_token": "optional when enabled",
  "recaptcha_token": "optional when enabled"
}
```

`name` is required, max 255; `email` is required and must be valid; `message` is required string. When CAPTCHA is enabled, the custom CAPTCHA rule is attached to `turnstile_token` and uses the expected action `contact`.

The recipient is read from the `mail_to_address` database setting, falling back to mail configuration. The message is sent immediately with `sendNow`; it is not queued by this controller. Success is HTTP 200 with message `Contact message sent successfully` and `data: null`. Mail exceptions return HTTP 500 with the exception text in the message. A migrated `app_settings` table is required because the database setting is queried before the fallback.

## Newsletter signup

```http
POST /api/mail/newsletter
```

```json
{
  "email": "subscriber@example.com",
  "name": "Jane Smith",
  "turnstile_token": "optional when enabled",
  "recaptcha_token": "optional when enabled"
}
```

Email is required and valid. Name is optional, max 255. The email is lowercased and trimmed. A new subscriber row is created with verification and unsubscribe tokens. A thank-you/verification email is sent synchronously to the exact subscriber address, and an admin notification email is sent immediately. The subscription becomes active only after the verification link is used. Success is HTTP 200 with `data.subscriber_id` and message `Newsletter signup processed. Please check your email to verify.`

If the email already exists, no new email is sent and the endpoint returns HTTP 200 with `data: null` and message `Email already subscribed`.

## Verify newsletter subscription

```http
GET /api/mail/newsletter/verify/{token}
```

An invalid token returns HTTP 404. A valid token sets `verified_at`, clears the verification token, and sends a final email confirming that the subscriber is successfully subscribed. JSON requests receive HTTP 200 with message `Subscription verified successfully` and `data: null`. Browser requests redirect to `FRONTEND_URL/newsletter/verified` when `FRONTEND_URL` is configured. A verified subscriber is normally unreachable because the token is cleared; if encountered, the controller returns `Subscription already verified`.

## Unsubscribe

```http
GET /api/mail/newsletter/unsubscribe/{token}
```

An invalid token returns HTTP 404. A valid token permanently deletes the subscriber row. JSON requests receive HTTP 200 with message `Successfully unsubscribed from newsletter` and `data.email`. Browser requests redirect to `FRONTEND_URL/newsletter/unsubscribed` when configured.

## Mail password-reset endpoint

```http
POST /api/mail/password-reset
```

```json
{ "email": "john@example.com" }
```

This is a separate implementation from `/api/auth/password/forgot`. It lowercases and trims the email, returns a generic HTTP 200 response for both known and unknown addresses, sends `PasswordResetMail` for known users, and stores a hashed token in `password_reset_tokens`.

**Flow limitation:** `/api/auth/password/reset` compares the submitted token directly with the database value, while this endpoint stores a hash. Therefore tokens generated by `/api/mail/password-reset` are not compatible with the current `/api/auth/password/reset` validation path. Use `/api/auth/password/forgot` for the reset flow consumed by `/api/auth/password/reset`.

# CAPTCHA

## Verify token

```http
POST /api/captcha/verify
```

Turnstile request:

```json
{
  "provider": "turnstile",
  "token": "captured-token",
  "action": "contact"
}
```

reCAPTCHA request:

```json
{
  "provider": "recaptcha",
  "token": "captured-token"
}
```

`provider` is optional and accepts only `turnstile` or `recaptcha`. When omitted, the controller always selects Turnstile; it does not auto-detect the enabled provider. `token` is required. `action` is optional and is passed to Turnstile verification when supplied.

The service calls the configured external verification endpoint. Success is HTTP 200 with message `Captcha verified` and the provider response in `data`. Failure is HTTP 422 with message `Captcha verification failed` and `errors.error` containing the provider result object.

## Data and security details implemented by the API

- User password fields are expected to be client-side SHA-256 strings of length 64 and are stored directly.
- User passwords and remember tokens are hidden from user JSON serialization.
- User email and username uniqueness is enforced by validation/database constraints, but user email is not consistently lowercased by authentication endpoints.
- Avatar uploads are stored on the public filesystem disk and returned as URLs.
- Payment `gateway_response` is hidden from serialized payment models; card last four and detected brand may be returned.
- The sandbox gateway accepts any webhook signature and is not a production payment integration.
- API plan creation, update, and deletion are public routes in the current code.
- AI job status is public and does not enforce ownership.
- No generic 60/minute or 10/minute throttles are registered for the routes described as standard/throttled in older documentation. Only `/api/ai/generate` has the named throttle shown above.
